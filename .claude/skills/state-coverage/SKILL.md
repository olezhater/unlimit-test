# State coverage — is every state in the spec actually reachable?

The spec defines 8 states (one of them the `/states` index itself, flagged
`excludeFromCoverageCount`), 5 statuses and 5 edge cases. `qaChecklist[1]` requires every state
to be reachable from `/states` in one click. This skill is how that is built and how it is
proved.

## 1. How a state maps to a URL

Every state is a URL, read from `location.search`. No in-memory-only state, no click path
required to arrive anywhere. The spec's `states[].route` is the contract — use it verbatim,
do not normalise it:

| `states[].id` | `states[].route` |
|---|---|
| `states_index` | `/states` |
| `empty` | `/?state=empty` |
| `loading` | `/?state=loading` |
| `list` | `/` |
| `filters_active` | `/?status=failed&currency=EUR` |
| `filters_no_results` | `/?status=rejected&currency=USD` |
| `details` | `/?tx=tx_1004` |
| `error` | `/?state=error` |

Two kinds of parameter, and the distinction matters:

- **`?state=`** forces a presentational state that real data cannot produce on demand
  (`empty`, `loading`, `error`). It is a prototype affordance and overrides the fixture list.
- **`?status=`, `?currency=`, `?tx=`** and the other `filters[]` ids are *real* application
  state. They must produce their result by actually filtering `fixtures[]` or selecting a
  fixture by id — never by a hardcoded branch keyed to the demo URL. `/?status=failed` must
  work because tx_1007 is failed, not because the string `failed` was special-cased.

`?tx=<id>` is orthogonal to the rest: it opens the details panel over whatever list state the
other parameters produce, per `states.details.behaviour`.

### The `/states` index

`/states` is the `states_index` entry in `states[]`. It is screenshotted like any other
route but carries `excludeFromCoverageCount`, so it is not one of the 17 counted entries. It
renders one entry per row, generated by mapping over the spec, never hand-listed:

- every `states[]` entry — `name`, `trigger`, link to `route`;
- every `statuses[]` entry — `label`, link to `/?tx=<a fixture with that status>`;
- every `edgeCases[]` entry — `requirement`, link to its own `edgeCases[].route`.

If a new entry is added to the spec, it appears on `/states` with no code change. An index
that needs editing when the spec changes is itself a defect.

## 2. What "covered" means

A state is covered only when **all three** hold. Two out of three is missing, not partial.

1. **Reachable** — pasting the route into a fresh tab renders that state, with no prior
   navigation, no click, no seeded storage. Reload keeps it.
2. **Renders from spec data** — the rows, amounts, counterparties, timestamps, references
   and rates on screen come from `fixtures[]`; the surrounding chrome comes from the spec's
   `copy`/`label` keys. Nothing on screen was authored in a component.
3. **Copy matches the spec string exactly** — character for character, including capitals,
   punctuation and the trailing period. `"No transactions yet"` is covered;
   `"No transactions yet."` is not. For templated strings, the non-placeholder text matches
   exactly and the substituted values come from the fixture.

## 3. Verification procedure

Run against the **running prototype**, not the source. Start `npm run dev`, then walk the
three arrays in order. Report every entry — including the passes. Load every route with
`?chrome=off` when judging product UI; the prototype bar is scaffolding.

Four behaviours cut across routes and must be checked wherever they apply:
- **Narrowed day totals** (`accountScope`, `groupHeaderExtra.narrowing`): "All accounts" is an
  option from every scope; under each single-account scope the day headers match
  `expectedDayTotals.scoped[<account>]`, and under each single-currency filter they match
  `expectedDayTotals.currencyFiltered[<currency>]` — a conversion counting only its matching leg.
- **Selection** (`states.list.defaultSelection`): at 1440+ the column always holds a visible
  transaction — the newest on load, the newest remaining when the selection is filtered or
  searched away. Below 1440 nothing is selected on load and the drawer closes when its
  transaction leaves the visible set. With nothing visible the column collapses. Walk filter
  combinations and confirm no hidden transaction is ever open.
- **Focus** (`defaultSelection.focus`, `states.details.focusBehaviour`): default selection moves
  no focus — the first Tab reaches the header, not a row. Click or Enter leaves focus on the
  row; the drawer takes focus and returns it to the row on close.
- **Sticky bar** (`listBehaviour.stickyBar`): scroll the list and confirm the bar is pinned at
  the top of the list region and one day header is pinned directly beneath it. Check it in both
  scroll modes — the window (`?chrome=off`) and the stage (chrome shown).

**Pass A — `states[]` (7 counted entries, plus `states_index`).** For each:
1. Open `states[].route` in a fresh tab.
2. Confirm the state named by `id` is what rendered — check against `behaviour`, not vibes.
   `loading` must show the skeleton described in `states.loading.behaviour` (two day groups of
   three rows, skeleton group headers, no spinner, held ≥300ms). `error` must keep the page
   frame, account scope dropdown and toolbar rendered and replace only the list region.
3. Diff every visible string against that state's `copy` object.
4. `filters_active`: confirm each active filter is a chip showing field and value
   (`"Status: Failed"`), each chip has a remove control, `Clear all` is present, the count
   reads `"{n} of {total} transactions"` with real numbers, and day-group totals reflect the
   filtered set (`qaChecklist[6]`; under a currency filter `qaChecklist[31]`).
   Open the Filters drawer and confirm every control has a valid resting state
   (`qaChecklist[34]`): Date on "All", Amount showing its "From" and "To" placeholders, Recipient or
   sender on "All" — and that Reset returns them there. Walk the counterparty combobox by
   keyboard alone (`qaChecklist[35]`): Down/Up, Enter, Escape (list closes, drawer stays),
   Tab; no browser autofill list.
5. `details`: confirm the body renders the `states.details.sections[]` entries whose
   `renderWhen` applies — in that order, and only those (`sectionsRule`: section count varies
   by transaction by design). Confirm that the pinned header carries avatar, amount, status badge, counterparty and the
   status block (no heading, no separate date; collapsed it is a plain line with "More"), and that
   Details holds the `sections[details].fields` the transaction has (Transaction ID last), as rows, each with a 44px copy
   control; Note follows as its own section on every transaction (heading naming a full-width filled field), and the
   actions sit in a footer pinned to the panel's bottom edge at 1440 and in the 1280 drawer. Repeat (`repeatAction`) shows on every non-incoming transaction and shows the stub notice. At a frame of
   1440px and above, confirm the column has no close control, Escape and outside clicks leave
   it filled, and swapping a transaction changes no column width and re-truncates no row. Below 1440px, confirm no
   panel on load, and that a row click opens the drawer with a scrim, closed by Escape, the
   close control and a scrim click, each returning focus to the row.

**Pass B — `statuses[]` (5 entries).** Each status must be visible in the list *and* in the
panel. For each:
1. Name a fixture carrying it: `in_progress` → tx_1002, `completed` → tx_1001,
   `rejected` → tx_1005, `cancelled` → tx_1006, `failed` → tx_1007.
2. In the list at `/`, confirm `listTreatment`: `amountStyle` (`regular` vs `strikethrough`),
   `statusPosition` (first element of the meta line, before the time, on the four exception
   statuses), `emphasis` and the `badge` composition. The four exception statuses carry their
   icon and a visible label; Completed rows carry no mark at all (`markVisible: false`), and
   the row's accessible name still contains "Completed". The meta line shows the note where
   there is one and never the payment reference (`rowAnatomy.metaNote`).
   Confirm `countsInDayTotal`: only Completed contributes to a day total.
3. At `/?tx=<id>`, confirm the badge, the `detailHelperText` string (or
   `detailHelperFallback` where the fixture lacks the templated field, or the fixture's own
   `reason` where `reasonOverride` applies — the two never render together), the
   `timeline.steps` with
   `currentStep` / `completedSteps` / `terminalStep` as given, rendered with the per-type
   labels of `timelineRules.steps`, the accordion open by default for every status except
   Completed (`timelineRules.expandedByDefault`), the helper suppressed where `showWhen` is
   `never`, one copy control per `copyableFields` entry present and none on any other field (`qaChecklist[28]`), and permanently visible, and that `primaryAction` and
   `secondaryAction` match — including `null`, which means the control is absent, not disabled.
4. Confirm all four `statusDifferentiation.channels` are present for that status.

**Pass C — `edgeCases[]` (5 entries).** For each, open `/?tx=<edgeCases[].fixture>` and check
the `rule` on both surfaces:
1. `long_counterparty` (tx_1007) — one line with ellipsis in the row, native `title`
   attribute present, full value wrapping to max three lines in the panel.
2. `long_reference` (tx_1007) — absent from the row (the row shows the note), never truncated
   in the panel, wraps in full, copy control present.
3. `fx_conversion` (tx_1003) — target amount primary and positive, source grey and negative
   underneath in the row; the five-line `fxModel.detailsBreakdown` plus the locked rate in
   the panel. The arithmetic must hold on screen: `sourceAmount = convertedAmount + fee` and
   `targetAmount = convertedAmount × rate`.
4. `fee_linking` (tx_1004 + fee_1004a, tx_1009) — tx_1004's row carries the
   `incl. {amount} {currency} fee` line and the split in its breakdown; **fee_1004a never
   appears as a top-level row in any filter combination** (`qaChecklist[3]`); tx_1009 has its
   own row; filtering type `Fee` returns tx_1009, tx_1004 **and** tx_1003 (`qaChecklist[4]`).
   Per `feeModel.conversionException`, tx_1003's row shows its source amount, not its fee.
5. `no_logo` (tx_1002, tx_1007) — lettermark circle (first letter of the name) with a type
   badge carrying the direction glyph at lower right; the same lettermark when a logo request
   fails; tx_1003 and tx_1009 use their category glyph.

Also confirm the panel's close control and copy control each carry an accessible name from
`states.details.copy`, and that every panel label comes from `fieldLabels` — `sections[]`
describes the panel and is not a source of labels.

**Report format.** One table, every entry, no omissions:

```
| Spec entry            | Array      | Route              | Covered | Note                     |
|-----------------------|------------|--------------------|---------|--------------------------|
| filters_no_results    | states     | /?status=rejected&currency=USD | yes | chips visible, copy exact |
| completed             | statuses   | /?tx=tx_1001       | no      | detailHelperText renders raw {deliveredAt} |
```

`Covered` is `yes` or `no` only. A check you could not run is `no` with the reason in the
note — never a pass. End with the count: `n of 17 covered`.

## 4. Empty vs no-results must be distinguishable

`states.filters_no_results.behaviour` calls this out explicitly: the user has to see that
their filters caused the blank list, not that their account is empty. `qaChecklist[5]` makes
it a gate. The two states differ on three axes, and all three are required:

| | `empty` (`/?state=empty`) | `filters_no_results` (`/?status=rejected&currency=USD`) |
|---|---|---|
| Toolbar (search, Date, Filters) | **hidden** (`behaviour`: hidden, not disabled) | **visible** |
| Filter chips | none | **all active chips visible above the block** |
| Headline | `No transactions yet` | `No transactions match your filters` |
| Body | `When you send or receive money, it will show up here.` | `Try a different date range, or clear some filters to see more.` |
| Primary action | `Make a transfer` | `Clear all filters` |

**How to check it.** Not by reading the code — by comparing the two renders:

1. Screenshot both routes at 1440×900.
2. Confirm all five rows of the table above differ as specified. Identical copy in either
   direction is a blocker.
3. **The chips are the load-bearing difference.** Confirm at least one chip is rendered above
   the no-results block and that none is rendered on `empty`.
4. **Crop test:** crop both screenshots to the centred block alone, discarding the chrome. The
   two must still be tellable apart from the headline and the action label. If the cropped
   blocks are indistinguishable, the states rely on surrounding chrome the user may have
   scrolled past — a defect.
5. Confirm the no-results primary action actually clears the filters and lands on `/`, and that
   the empty-state action is not wired to a filter operation.
6. Confirm the no-results state is **reachable through the filter UI alone** — both Rejected
   and USD are selectable, so no typed URL is needed (`qaChecklist[5]`).
